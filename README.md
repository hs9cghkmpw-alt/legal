# ルール便（MVP・仮称）

個人・法人を分けず、登録時に立場からカテゴリを提案し、利用者が選んだカテゴリに合うルール変更情報を届ける試作版です。

## ブランド・LP
- 利用者向けの仮称は「ルール便」。説明文は「暮らし・仕事・事業に関わるルール変更を、公式情報をもとに整理してメールでお届け」。
- ファーストビューで価値・配信方法・登録CTAを提示し、メールの見本、特徴、3ステップ、注意事項、登録フォームの順に構成。
- LPは外部画像・フォント・分析サービスを使わず、レスポンシブCSSで構成。名称の商標・ドメイン確認は未実施。

## 登録体験
- 登録開始時は4つのおすすめセットから選べ、分野の詳細調整や立場による推薦は任意で開ける。
- 登録頻度・空週の扱い・配信停止・公式原文確認の必要性を登録前に説明。
- プライバシー方針URLに加えて `SIGNUP_ENABLED=true` が設定されない限り、画面と登録APIの両方で受付を停止する。フラグは利用条件・プライバシー・配信運用の確認が完了するまで有効化しない。
- 改善理由と未解決リスクは `docs/ONBOARDING_REVIEW.md` に記録。

## 編集品質・情報源確認
- `docs/SOURCE_REUSE_REVIEW.md`：e-Gov APIとデジタル庁RSSの再利用条件に関する暫定確認。最終判断は未完了で、`terms_checked=0` を維持。
- `docs/EDITORIAL_QA.md`：原文照合・承認・訂正の基準。
- `docs/SAMPLE_ARTICLE_DRAFT.md`：国土交通省の実際の発表を根拠にした内部候補。未承認であり、公開サンプル・配信に使用しない。

## 現状・制限
- 未デプロイ。実データ、実メール、無料枠、セキュリティの検証は未実施。
- 情報源候補はデジタル庁RSSと e-Gov法令API Version 2。両方とも利用条件確認前は `terms_checked=0` のまま収集停止。
- e-Gov APIは法令一覧を1ページずつ走査し、改正公布日が直近7日以内の候補を抽出。APIの並び順を全体で保証されるものと仮定せず、1回最大10候補を処理し、ページ内位置を10分Cronで再開する。
- これは改正候補の検出であり、全件検出や改正内容の自動解釈を保証しない。記事は承認待ちで保存し、改正本文・施行日・経過措置は原文確認が必要。
- 外部AI APIは未使用。記事の原文確認・解説入力・承認は手作業。
- 配信メールには情報源名・公式原文リンク・ルール便による編集表示を付ける。情報源ごとの利用条件は別途確認し、未確認の情報源は有効化しない。
- 登録APIはプライバシー方針のHTTPS URLと `SIGNUP_ENABLED=true` の両方が必要。画面だけでなくサーバー側でも受付を停止する。
- `SIGNUP_ENABLED` が `true` でない場合、週次配信キューの作成と既存キューからのメール送信も停止する。停止中のキューは削除せず、準備完了後に運用判断のうえ再開する。
- 配信対象のキュー作成も50登録者ずつ再開可能なバッチで処理し、10分ごとに継続。実際のメール送信は1回最大20人、明確な失敗は最大5回まで再試行。
- 配信中にWorkerが停止した `sending` 行は自動で `pending` に戻さない。メール配信事業者が受理した可能性があるため、重複防止を優先し、手動確認が必要。
- 送信結果がネットワーク障害などで不明な場合や、事業者受理後にDB確定処理が失敗した場合は `failed` として自動再送を止める。結果不明・失敗・処理中のキューに含まれる記事は、次回以降の週次キューにも自動で再登録しない。未配信の可能性がある記事は手動で照合する。
- 外部メール事業者とD1間に分散トランザクションや共通の冪等キーがないため、厳密な exactly-once 配信は保証できない。現実装は重複送信の自動発生を抑える代わりに、一部の不確定ケースで配信漏れの可能性を残す。
- 事業者の応答やWorker停止のタイミングによって送信結果を自動判定できないケースは残るため、運用時は `sending` / `failed` の状態と事業者側ログを照合する。
- 無料枠の維持・自動課金なしは、Cloudflareとメール配信サービスの設定・規約確認が必要。

## ローカル開発
```powershell
npm install
Copy-Item .dev.vars.example .dev.vars
npm test
npx wrangler d1 execute rule-change-letter --local --file=./schema.sql
npx wrangler dev
```

このプロジェクトは未デプロイの試作版です。新規のローカルDBで `schema.sql` を使用してください。既存D1データベースがすでにある場合は、現時点で安全な移行SQLが同梱されていないため、`schema.sql` を再実行せず作業を止めてください。

## 管理API
- `POST /api/admin/collect` — 収集（Bearerトークン必須）
- `GET /api/admin/updates` — 承認待ち記事一覧（Bearerトークン必須）
- `POST /api/admin/approve` — 記事承認（Bearerトークン必須）
- `POST /api/admin/send` — キュー作成と最大20人の即時処理（Bearerトークン必須）

## 配信キューの手動照合

配信結果が不明な行の確認と復旧手順は `docs/DELIVERY_RECONCILIATION.md` を参照してください。事業者ログで受理・未受理を確認してから操作し、結果が不明なまま再試行しないでください。

## 公開・登録受付フラグ
- `SIGNUP_ENABLED` は既定で無効です。準備が完了するまで設定しないでください。無効時は新規登録に加えて、スケジュール配信のキュー作成とメール送信も停止します。
- 有効化は、情報源の利用条件、プライバシー方針・運営者情報、原文確認と訂正の手順、実メール・停止・削除テスト、送信元認証の確認後に限ります。

## URL設定
- ローカル開発では `.dev.vars` の `BASE_URL=http://localhost:8787` を使用します。
- 公開環境では `BASE_URL` に実際のWorkerのHTTPS URLを明示設定してください。未設定・HTTPの公開URLでは登録を拒否し、確認メールにlocalhostリンクが入る事故を防ぎます。

## 公開前必須
情報源の利用条件、プライバシー方針、運営者情報、ボット対策、メール送信元認証、Cloudflare/Brevoの無料枠、Cron制限、バックアップ、配信停止を確認してください。公布日と施行日を混同しないこと。
